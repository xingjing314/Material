# AI阅读说明

本文讨论的不是“如何写一个更规范的JSON文件”，而是一个更高层次的问题：

> **如何让未来AI系统的业务定义尽量脱离具体程序实现，通过统一的声明式实体、关系与映射进行表达，并由Runtime解释和执行。**

本文使用“类Linux”作为架构类比。这里并不是模仿Linux的具体实现，而是借鉴其通过稳定抽象和统一原语隔离上层语义与底层实现的思想。

因此，阅读本文时必须区分三个层次：

1. **长期架构方向**：未来希望具备什么能力；
2. **设计预留原则**：现在的JSON不能堵死什么能力；
3. **当前实现要求**：现阶段真正需要建设什么。

其中：

> **长期方向 ≠ 当前实现任务。**

当前软考AI仍处于产品设计阶段。本文现阶段最重要的作用，是指导后续领域JSON的设计，使其未来可以进入更完整的声明式AI操作系统体系，而不是现在提前建设完整的Registry、Graph Runtime、权限中心、Schema Registry或Control Plane。



# AI操作系统声明式JSON设计原则与演进边界

> 日期：2026-08-09  
> 文档性质：设计原则说明 / 上位架构约束  
> 当前适用范围：软考AI产品设计阶段及后续能力体系、能力编排、Agent、MVP、生产实现  
> 当前状态：原则性定义，非完整实现规范  
> 核心目的：在当前保持产品设计简洁的前提下，为未来扩展到“类 Linux 的 AI 操作系统声明体系”预留结构能力，避免后期因 JSON 语义、关系、契约和运行时职责混杂而发生高成本重构。

---

# 1. 文档背景

软考AI当前已经开始使用 JSON 描述平台目标、产品边界、用户特征、业务字典等产品语义。

例如：

```json
{
  "platform_goal": {
    "core_goal": "通过考试",
    "description": "定义软考AI平台最高且不可被用户个体目标、知识背景、学习偏好或其他产品能力改变的核心目标，以及为防止产品定位漂移而设定的边界。",
    "exclusions": [
      {
        "id": "boundary.no_deep_technical_training",
        "name": "不扩展为深层技术培训",
        "description": "技术知识的讲解和扩展仅服务于理解软考内容、建立考试所需认知和应对真实考试，不以培养软件开发、架构、AI、云计算等专项技术应用能力为目标。"
      }
    ]
  }
}
```

在当前阶段，这类 JSON 主要承担：

- 业务概念描述；
- 数据定义；
- 业务字典定义；
- 产品规则和边界声明。

但未来希望逐步扩展为：

```text
第一阶段：
JSON value 由研发人员维护
        ↓
第二阶段：
JSON value 可由专门平台维护
        ↓
第三阶段：
JSON key、value、关系、映射均可由平台维护
        ↓
第四阶段：
通过调整实体、关系、权限、策略、映射和编排，
在较少修改底层代码的情况下改变产品结构和业务方向
```

因此，当前 JSON 不能只从“配置文件”或“给 LLM 看的结构化文本”角度设计。

需要从更高层理解为：

> **未来 AI 操作系统的声明式业务语言载体。**

---

# 2. “类 Linux”设计思想

本文所说的“类 Linux”，不是模仿 Linux 的目录、命令或内核实现。

借鉴的是 Linux 的核心抽象思想：

> **通过少量稳定原语和统一接口，对大量不同资源进行抽象，使上层不必理解底层具体实现。**

在本体系中，对应的目标是：

> **Everything is Declarative**

即：

> 业务实体、能力、动作、关系、权限、策略、层级、映射、编排等重要业务概念，尽量能够通过统一的声明体系描述。

底层实现可以不同：

```text
Java
Python
LLM
RAG
Agent
MCP Server
HTTP API
数据库
普通函数
远程服务
```

但业务层原则上不直接依赖这些实现。

---

# 3. 核心架构思想

整个体系最终希望形成：

```text
声明式业务世界
    │
    ├── Entity Definition
    ├── Action Definition
    ├── Relation Definition
    ├── Policy Definition
    ├── Permission Definition
    ├── Mapping Definition
    ├── Graph / Orchestration Definition
    └── Contract Definition
             │
             ↓
        Runtime / Interpreter
             │
      ┌──────┼──────┐
      ↓      ↓      ↓
    Java   Python   LLM/Agent
```

因此：

> **软考AI的业务本体应尽量由“声明 + 映射”定义，开发语言主要承担实现和执行。**

---

# 4. AI操作系统利用JSON设计的原则

## 4.1 统一声明原则（Everything is Declarative）

AI操作系统中的重要业务概念应尽量能够通过统一声明体系定义，包括但不限于：

- 业务实体；
- 用户特征；
- 平台目标；
- 知识；
- 能力；
- 动作；
- 关系；
- 权限；
- 策略；
- 层级；
- 映射；
- 调用图；
- 编排。

JSON 是当前主要声明载体。

但不把 `.json` 文件格式本身视为不可替换的最终形态。

---

## 4.2 声明而不执行（Declare, not Execute）

JSON负责声明：

- 是什么；
- 能做什么；
- 需要什么；
- 产生什么；
- 有什么边界；
- 有什么关系；
- 谁可以使用；
- 如何组合。

JSON自身不执行具体业务逻辑。

执行由 Runtime 和具体 Provider 完成。

因此：

```text
声明动作
    ≠
实现动作
```

---

## 4.3 业务定义高于开发语言

领域 JSON 不依赖：

- Java Class；
- Python函数；
- LangGraph Node；
- 数据库表；
- MCP方法；
- 某个具体LLM；
- 某个具体Agent框架。

允许存在“实现映射”，但实现映射不成为业务定义本身。

原则：

> **Contract over Implementation**

---

## 4.4 实体是一等公民

所有具有独立业务身份和生命周期的概念均可以成为实体。

例如：

- Goal；
- User Feature；
- Knowledge；
- Capability；
- Policy；
- Agent；
- Resource；
- Model；
- Environment。

实体负责描述自身语义。

---

## 4.5 动作是一等公民

动作不能天然等同于一段代码。

例如：

```text
evaluate_user
generate_learning_plan
retrieve_exam_knowledge
assess_mastery
```

动作本身应允许被声明。

动作的具体实现可以映射到：

- Java；
- Python；
- LLM；
- Agent；
- RAG；
- MCP；
- HTTP API；
- 其他 Provider。

---

## 4.6 关系是一等公民

以下关系不应只能隐藏在代码中：

```text
A constrains B
A depends_on B
A belongs_to B
A references B
A can_call B
A implements B
A maps_to B
```

关系应允许被独立声明、校验、发现和审计。

---

## 4.7 实体描述自己，关系外置

原则：

> **Self-description, External Relationship**

实体本身主要负责：

- 我是谁；
- 我是什么；
- 我的语义；
- 我的内部组成；
- 我的边界。

实体原则上不负责主动记录：

- 谁创建了我；
- 谁在使用我；
- 谁能调用我；
- 我属于哪个具体业务链；
- 我当前参与哪个产品流程；
- 谁依赖我。

这些关系应由：

- Relation；
- Mapping；
- Policy；
- Permission；
- Graph；

等外部声明对象表达。

---

## 4.8 业务定义与业务挂接分离

能力模板只定义能力本身。

它不天然属于：

- 软考AI；
- 法律AI；
- 某个Agent；
- 某个Workflow。

业务挂接由 Mapping 定义。

因此：

```text
Capability Definition
        ≠
Business Binding
```

同一个能力可以被多个产品复用。

---

## 4.9 定义与映射共同组成产品

Definition 回答：

> **系统里有什么？**

Mapping 回答：

> **这些东西如何组成当前产品？**

因此产品不是单纯由若干 JSON Definition 构成，而是：

> **Definition + Mapping**

例如：

```text
能力 A
能力 B
能力 C
能力 D
```

软考AI可以映射为：

```text
A → B → C
```

其他产品可以映射为：

```text
A → D → C
```

能力自身不需要知道自己属于哪一个产品。

---

## 4.10 调用图和编排可以成为数据

调用关系未来可以声明为独立 Graph / Mapping Entity。

例如：

```text
A → B → C
```

不要求：

- A 知道 B；
- B 知道 C；
- Java代码拥有全部业务编排权。

Graph 描述组合关系，Runtime负责解释执行。

---

## 4.11 Definition、Instance、Runtime State 严格分离

必须区分：

### Definition

定义概念本身。

例如：

```text
“薪资提升”这个参与目标是什么意思？
```

### Instance

具体业务对象的取值。

例如：

```text
用户A的参与目标 = 薪资提升
```

### Runtime State

当前运行状态。

例如：

```text
Agent当前执行到第3步
用户本次学习任务处于进行中
```

原则：

> **Definition ≠ Instance ≠ Runtime State**

三者不得长期混合在同一种业务 JSON 中。

---

## 4.12 稳定身份原则

所有具有以下任意特点的对象应拥有稳定 ID：

- 可能被其他对象引用；
- 可以独立修改；
- 有独立生命周期；
- 需要被日志定位；
- 需要审计；
- 可能被发现；
- 可能被映射；
- 未来可能改名但仍代表同一个概念。

推荐语义化 ID，例如：

```text
boundary.no_deep_technical_training
goal.salary_growth
goal.talent_settlement
knowledge.software_development
```

原则：

> `name` 和 `description` 可以变化；概念本身未发生改变时，ID原则上不变。

如果概念核心语义已经发生变化，应考虑创建新 ID，而不是静默改变旧 ID 的含义。

---

## 4.13 ID生成规则统一管理

ID不应由不同开发者随意创造不同风格。

未来应由统一规则或专门功能负责：

- namespace；
- 命名规则；
- 唯一性检查；
- 冲突检测；
- 生命周期管理。

当前阶段先确定原则，不要求立即开发 Registry。

---

## 4.14 领域Key统一命名

领域 JSON 当前统一建议使用：

> `snake_case`

例如：

```json
{
  "platform_goal": {},
  "core_goal": "",
  "source_documents": []
}
```

原因不是 `snake_case` 天然优于其他风格，而是：

- 与当前领域文件一致；
- 长业务词可读性较好；
- 不绑定 Java / JavaScript / Python 任意一种语言；
- LLM和人类都容易解析。

外部标准协议的标准字段必须保持原规范名称，不进行强制转换。

---

## 4.15 语义说明统一使用 `description`

领域对象自然语言说明统一优先使用：

```text
description
```

不再新增多个同义字段，例如：

```text
remark
desc
explain
note
```

除非它们具有不同且明确的业务语义。

---

## 4.16 规范性语义、业务数据、机器Schema分离

未来至少区分：

```text
Normative Semantic Specification
        ↓
规范性语义说明

Canonical Domain Definition
        ↓
业务语义数据

JSON Schema
        ↓
机器结构契约
```

三者职责不同。

---

## 4.17 JSON Schema只负责结构契约

JSON Schema用于判断：

- 字段是否存在；
- 类型是否合法；
- 数量是否符合；
- 是否允许未知字段；
- 对象结构是否合法；
- 可复用结构是否合法。

但：

> **结构正确 ≠ 业务语义正确。**

---

## 4.18 语义完整性规则独立存在

未来还需要独立的 Semantic Integrity Rules，用于验证：

- 引用对象是否真实存在；
- Relation 是否允许连接这两类对象；
- 是否形成禁止的循环依赖；
- 是否出现非法层级穿透；
- 是否引用了不允许依赖的 Runtime；
- 下层定义是否试图覆盖上层不可覆盖规则。

不能把这些职责全部压给 JSON Schema。

---

## 4.19 显式依赖原则

实体之间的重要依赖应尽量显式声明。

系统最终应该能够形成：

> **Dependency Graph**

从而支持：

- 影响分析；
- 变更分析；
- 循环依赖检测；
- 发布检查；
- 回滚判断。

---

## 4.20 允许合理跨层引用，不简单禁止跨层

跨层引用不是天然错误。

例如：

```text
Persona
    references
Goal Definition
```

可以合理存在。

真正需要限制的是：

- 实现层污染领域层；
- 非法反向依赖；
- 循环依赖；
- 未授权层级穿透；
- 语义不合理的引用。

因此未来应依赖统一的 Layer / Dependency Rule，而不是简单规定：

> “所有跨层调用禁止”。

---

## 4.21 结构开放性与权限是两个不同问题

必须区分：

### Structure Openness

允许不允许未知 key。

### Access Permission

谁能：

- 读；
- 写；
- 修改；
- 发布；
- 调用。

两者不能混为一个“开放/只读”概念。

---

## 4.22 稳定核心结构应趋向封闭

设计早期可以允许快速调整。

正式发布后的核心契约应趋向严格：

- 明确 properties；
- 明确 required；
- 限制任意未知字段；
- 扩展通过明确机制进行。

避免因为拼写错误或随意增加字段造成静默失效。

---

## 4.23 Schema与业务JSON分文件

推荐未来采用：

```text
domain/
    platform_goal.json

schemas/
    platform_goal.schema.json
```

职责：

```text
platform_goal.json
    ↓
描述业务事实

platform_goal.schema.json
    ↓
验证业务事实的机器结构
```

业务 JSON 不承担 Schema 本身的职责。

---

## 4.24 Schema身份与业务实体身份分离

未来可能同时存在：

```text
$id
```

和：

```text
id
```

两者含义不同：

```text
$id
    → JSON Schema Resource 的身份

id
    → 业务领域实体的身份
```

不能混用。

---

## 4.25 契约版本与内容修订分离

未来版本至少要区分：

- 领域契约版本；
- Schema版本；
- 内容修订；
- 文档版本；
- API/协议版本。

不能用一个模糊的 `version` 表达所有概念。

基本兼容性原则：

### Major

消费者需要迁移才能正确工作，例如：

- 删除字段；
- 改字段类型；
- 修改核心语义；
- 修改 ID 规则；
- 改变 Definition / Instance 职责边界。

### Minor

理论上兼容的结构能力扩展。

### Patch

不改变机器结构和核心语义的修正。

具体版本治理在开发阶段再正式定义。

---

## 4.26 Canonical Source of Truth 原则

原始领域定义是唯一权威业务源。

例如：

```text
Canonical Domain Definition
```

不能长期维护：

```text
领域版
LLM版
MCP版
UI版
```

四套彼此独立的业务事实。

---

## 4.27 消费者通过 Adapter / Projection 使用领域定义

未来可能形成：

```text
Canonical Domain JSON
        ↓
     Projection
   ↙     ↓      ↘
 LLM    MCP     UI
 View   View    View
```

消费者不能反过来迫使领域模型按自己的协议生长。

原则：

> **Consumer adapts to Domain, not Domain adapts to Consumer.**

---

## 4.28 Projection必须可再生

Projection必须：

- 从 Canonical Definition 自动生成；
- 不成为第二份业务事实源；
- 不允许长期手工独立修改；
- 能追踪来源实体；
- 能追踪来源版本。

因此“投影”不是复制另一套 JSON。

---

## 4.29 能力发现与能力定义分离

当未来实体数量很大时，LLM / Agent 不应一次读取全部 Definition。

未来应允许：

```text
Catalog / Registry
        ↓
先发现有什么
        ↓
按需读取完整定义
```

类似：

```text
list / search
        ↓
inspect / read
        ↓
use / execute
```

当前阶段只预留，不实现完整 Catalog。

---

## 4.30 权限本身也是声明对象

未来可以用 Permission / Policy 定义：

- 谁可以读；
- 谁可以写；
- 谁可以调用；
- 谁可以建立关系；
- 哪些实体可以操作哪些实体；
- 哪些动作允许作用于哪些对象。

避免将大量权限判断散落在业务代码中。

---

## 4.31 治理与业务定义分离

以下信息属于 Governance / Control Plane：

- 谁创建；
- 谁修改；
- 谁审核；
- 谁发布；
- 何时生效；
- 变更原因；
- 是否废弃；
- 是否允许回滚；
- 谁依赖它。

不要求全部写进每一个业务实体自身。

---

## 4.32 Runtime是解释器，不是业务本体

Runtime负责：

- 解析 Definition；
- 解析 Relation；
- 解析 Mapping；
- 校验 Policy；
- 检查 Permission；
- 选择 Provider；
- 执行 Graph；
- 保存 Runtime State。

业务本体不应永久绑定某一版 Runtime。

目标是：

> Runtime可以重写，业务声明尽量能够保留。

---

## 4.33 同一能力允许多个实现Provider

例如：

```text
capability.evaluate_user
```

可以在不同阶段映射到：

```text
Python Provider
Java Provider
LLM Provider
Agent Provider
MCP Provider
Remote API Provider
```

业务依赖：

> Capability Contract

而不是依赖具体 Provider。

---

## 4.34 JSON声明体系最终可以演化为Control Plane

当平台能够维护：

- Entity；
- Action；
- Relation；
- Mapping；
- Permission；
- Policy；
- Layer；
- Graph；

以后，修改声明可能会影响整个系统行为。

因此最终必须支持：

- 审计；
- 影响分析；
- 依赖检查；
- 版本治理；
- 审批；
- 发布；
- 回滚。

这属于未来 AI 操作系统级能力。

---

## 4.35 JSON是载体，不把文件格式神圣化

长期稳定的核心不是：

> `.json` 文件。

而是：

> **统一声明原语 + 稳定身份 + 契约 + 关系 + 映射 + Runtime解释执行。**

未来数据可以存储在：

- JSON文件；
- 数据库；
- 图数据库；
- 对象存储；
- Registry；
- DSL；
- 其他结构化存储。

只要其领域语义保持一致。

---

## 4.36 当前只预留，不提前实现完整AI操作系统

当前仍处于软考AI产品设计阶段。

现在要做到的是：

> **后续产生的 JSON 不堵死未来演化能力。**

当前不要求立即建设：

- Schema Registry；
- Domain Registry；
- Permission Center；
- Graph Runtime；
- Control Plane；
-完整版本迁移系统；
- 通用工作流引擎；
- 通用AI操作系统内核。

否则会发生过度设计并偏离当前产品目标。

---

# 5. 五条最高设计原则

如果将上述原则进一步收敛，可以归纳为以下五条：

## 5.1 Everything is Declarative

重要业务概念尽量可以通过统一声明体系表达。

---

## 5.2 Declare, not Execute

声明负责定义，Runtime负责执行。

---

## 5.3 Self-description, External Mapping

实体描述自己。

业务关系、挂接、调用、权限和编排由外部 Mapping / Relation / Policy 等实体定义。

---

## 5.4 Contract over Implementation

业务依赖稳定契约，不依赖 Java、Python、LLM、Agent 或其他具体实现。

---

## 5.5 Definition + Mapping + Runtime

最终系统可以理解为：

```text
Definition
    ↓
定义业务世界有什么

Mapping
    ↓
定义这些实体如何组成产品

Runtime
    ↓
解释和执行这些声明
```

这是“类 Linux AI 操作系统”设计思想的核心。

---

# 6. 当前JSON设计的直接要求

在当前软考AI产品设计阶段，每次新增 JSON 时至少检查：

1. 这个 JSON 是 Definition、Instance 还是 Runtime State？
2. 它是否只描述自身，而不是偷偷挂接业务？
3. 它是否知道了本不应该知道的其他实体？
4. 它是否混入 Java / Python / MCP / Agent 等实现细节？
5. 具有独立身份的对象是否有稳定 ID？
6. 自然语言解释是否统一使用 `description`？
7. key 是否遵循统一 `snake_case`？
8. 是否把业务关系硬编码进实体内部？
9. 未来是否可以通过独立 Relation / Mapping 把它挂接到其他业务？
10. 它是否仍然可以被未来的 Schema 单独验证？
11. 是否能够被未来 Catalog / Registry 发现？
12. 是否能够在不修改本体定义的情况下映射到不同 Provider？
13. 是否为未来版本、治理、审计和影响分析留下可能性？
14. 是否为了未来能力提前塞入当前不需要的复杂字段？

最后一项尤其重要：

> **预留能力，不等于预埋所有字段。**

# 8. 当前结论

当前软考AI的 JSON 不应仅被理解为：

> “结构化配置文件”。

更准确的定位是：

> **未来统一声明式业务体系的早期领域定义载体。**

长期目标不是：

> 所有业务代码都被 JSON 替代。

而是：

> **尽可能将业务世界的定义、关系和组合从具体实现代码中抽离出来，以稳定契约和声明体系描述；程序语言、模型和Agent负责实现这些声明。**

最终希望形成：

```text
AI软考业务世界
    =
声明式定义
    +
声明式映射
    +
可替换实现
    +
Runtime解释执行
```

这构成未来“类 Linux AI 操作系统”的基础设计方向。
