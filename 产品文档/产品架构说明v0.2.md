# 产品架构说明 v0.2

> 文档定位：本文件不是正式的产品设计待评审版，也不是系统架构设计文档。  
> 它用于描述当前阶段对“软考AI产品从机会识别到上线”的整体规划理解，帮助后续研究、产品设计、能力设计、MVP设计、系统设计和实现阶段保持同一条业务主线。
>
> 本文档优先表达**产品业务逻辑**，不提前绑定 JSON Schema、Agent、LangGraph、RAG、数据库、模型或其他具体技术实现。

---

# 1. 产品架构的总体目标

软考AI产品的最高平台目标是：

> **帮助用户通过考试。**

围绕这一目标，产品设计不能只回答：

> “用户有什么痛点，我们如何解决？”

还必须同时回答三类问题：

1. **用户价值**
   - 用户真正遇到什么问题？
   - 哪些问题会影响通过考试？
   - 产品解决后是否产生可感知价值？

2. **商业价值**
   - 用户为什么选择我们？
   - 为什么持续使用？
   - 为什么不用免费AI、教材、题库、培训机构等替代？
   - 用户为什么愿意付费？
   - 收入是否有机会支撑产品长期存在？

3. **实现可行性**
   - 产品承诺的价值是否能够被AI和工程系统稳定实现？
   - 数据、模型、成本、性能、安全、可维护性是否可接受？

三者必须同时成立。

```text
用户价值
   │
   ├──────────────┐
   │              │
   ▼              ▼
产品值得被使用    商业价值成立
   │              │
   └──────┬───────┘
          ▼
     产品值得被做
          │
          ▼
     实现可行性
          │
          ▼
       可落地产品
```

# 3. 横向机制

阶段是纵向推进主线，但以下机制不是单独某一个阶段的工作，而是贯穿多个阶段。

## 3.1 Validation / Eval

Validation 不应被理解为“开发完成后的测试”。

不同阶段验证不同类型的假设：

```text
阶段1～3：
验证我们对市场、用户、考试和问题的理解是否正确

阶段4：
验证用户价值、差异化、留存、付费和商业成立假设

阶段5～6：
验证产品方案与产品能力是否真的能解决选中的问题

阶段7：
验证MVP用户流程、核心体验和端到端场景

阶段8～9：
验证系统实现、AI质量、工程稳定性、真实用户效果和商业指标
```

## 3.2 用户价值、商业价值、实现可行性

这三条分析轴不应该被拆成三个孤立阶段。

任何重要产品决策都应至少考虑：

```text
用户是否需要？
        +
用户是否愿意持续使用 / 付费？
        +
我们是否能够稳定实现？
```

当前阶段应以**用户价值和商业价值优先**，技术实现作为可行性约束，而不是让技术结构反向决定产品。

# 4. 阶段划分

## 阶段1：机会与市场理解

### 核心目的

确认：

> **为什么存在值得做的软考AI产品机会。**

### 主要回答的问题

包括但不限于：

- 为什么用户参加软考？
- 软考给用户带来什么现实价值？
- 这个市场为什么存在？
- 用户目前通过什么方式备考？
- 教材、题库、培训机构、通用AI分别承担什么角色？
- 当前市场中有哪些明显未被满足的需求？
- AI的出现是否改变了原有产品机会？
- 市场空间是否值得进入？
- 机会是短期考试工具，还是可以形成持续产品？

### 输入

- 软考制度与市场背景；
- 用户参加考试的现实动机；
- 培训市场和备考方式；
- 现有产品和替代方案；
- AI产品发展带来的新可能性；
- 已知的行业经验和市场观察。

### 输出

- 市场与机会空间描述；
- 用户参加考试的主要动机；
- 现有解决方式概览；
- 初步机会假设；
- 值得继续研究的问题空间。

### 注意事项

本阶段不应提前承诺产品功能，也不应因为“AI能做”就认为“市场需要”。

---

## 阶段2：产品目标与原则

### 核心目的

确认：

> **如果做这个产品，平台最终负责什么，以及明确不负责什么。**

### 主要回答的问题

包括但不限于：

- 平台最高目标是什么？
- “通过考试”在产品中意味着什么？
- 哪些用户目标可以影响教学策略，但不能覆盖平台目标？
- 产品允许扩展到什么深度？
- 哪些事情即使用户提出，也不应成为平台长期定位？
- 教材在产品中的角色是什么？
- 外部知识可以扩展到什么程度？
- 产品设计应遵守哪些基本原则？

### 输入

- 阶段1的市场与机会理解；
- 对软考考试本质的初步认识；
- 用户现实价值诉求；
- 产品长期方向；
- 产品边界风险。

### 输出

- `Platform Goal`；
- 产品边界；
- 基础业务原则；
- 初始业务Definition；
- 用于后续研究的用户理解框架或假设。

### 注意事项

阶段2形成的用户分类或Definition，如果尚未经过真实用户研究，应被视为：

> **研究框架 / 初始假设**

而不是不可修改的用户事实。

---

## 阶段3：问题与现实研究

### 核心目的

建立对两个现实世界的理解：

```text
User Reality
+
Exam / Textbook Reality
        ↓
真正影响用户通过考试的问题
```

本阶段是产品发现的重要阶段。

### User Reality：主要回答的问题

包括但不限于：

- 谁在参加考试？
- 用户为什么参加考试？
- 用户现在如何学习？
- 用户真正担心什么？
- 哪些问题导致学习效率低？
- 哪些问题导致考试失败？
- 哪些问题导致中途放弃？
- 用户过去如何解决这些问题？
- 用户为什么购买培训课程？
- 为什么不购买？
- 用户为什么使用免费资源？
- 为什么会使用通用AI？
- 什么情况下会持续使用某个学习工具？
- 什么情况下会停止使用？
- 什么因素可能影响付费？
- 哪些用户问题是个体问题？
- 哪些可以形成共性问题或用户分类？

### Exam / Textbook Reality：主要回答的问题

包括但不限于：

- 通过考试实际要求用户掌握、理解和具备什么？
- 教材能够覆盖什么？
- 考试大纲能够覆盖什么？
- 真实考试还会额外要求什么？
- 教材、大纲和真实考试是否完全重合？
- 三个考试科目分别要求什么？
- 教材内知识是否需要跨章节、跨体系组合？
- 是否存在必要的教材外知识？
- 用户是否需要知识迁移、综合判断、表达或实践转换能力？
- 教材结构、篇幅与真实考试重要性是否一致？
- 哪些内容是稳定要求？
- 哪些内容具有不确定性？

### 输入

- 用户原始反馈与教学经验；
- 用户行为观察；
- 培训机构和替代方案观察；
- 官方教材；
- 官方考试大纲；
- 历年考试和考情资料；
- 对真实考试的领域经验；
- 多AI分析可以作为 Candidate Discovery，但不自动作为事实依据。

### 输出

- 用户个体问题；
- 用户共性问题；
- 用户分类或用户画像的候选结构；
- 用户购买、留存、放弃等行为现实；
- 教材与考试现实；
- 教材 / 大纲 / 真实考试之间的重要差异；
- 真正影响“通过考试”的问题集合；
- 后续产品定位需要验证的核心问题。

### 注意事项

本阶段重点是：

> **发现和理解问题。**

不是立即决定：

- 做什么功能；
- 用什么AI；
- 建什么Agent；
- JSON怎么设计。

---

## 阶段4：产品定位与商业验证

### 核心目的

从阶段3发现的大量真实问题中做产品选择：

> **我们到底为谁、解决什么、提供什么差异化价值，并验证用户是否愿意持续使用和付费。**

### 用户价值方向：主要回答的问题

包括但不限于：

- 服务谁？
- 解决什么？
- 为什么这个问题重要？
- 这个问题与“通过考试”的关系有多强？
- 解决后给用户带来什么价值？
- 为什么AI适合解决？
- 用户能否明显感知价值？
- 这个问题现有方案为什么没有解决好？
- 哪些问题第一版必须解决？
- 哪些问题可以暂不解决？

### 商业价值方向：主要回答的问题

包括但不限于：

- 为什么用户选择我们？
- 为什么不用普通AI？
- 为什么不用免费AI替代？
- 为什么不用教材、题库、培训机构替代？
- 为什么持续使用？
- 备考生命周期内如何形成有效留存？
- 用户为什么愿意付费？
- 愿意为什么价值付费？
- 哪些价值用户认为理应免费？
- 产品的差异化是否足够明显？
- 付费是一次性、订阅、课程制还是其他形式？
- 收入是否能支撑产品长期存在？
- 用户通过考试后自然离开是否属于正常成功结果？
- 商业模式是否有可能成立？

### 输入

- 阶段3的 User Reality；
- 阶段3的 Exam / Textbook Reality；
- 用户痛点和行为现实；
- 竞争与替代方案；
- 初步产品目标与边界；
- 用户价值和商业价值假设。

### 输出

- Target User；
- Core Problem；
- Value Proposition；
- Differentiation；
- Retention Hypothesis；
- Payment Hypothesis；
- 初步商业模式；
- MVP Boundary；
- Success Criteria；
- 需要继续验证的产品假设。

### 注意事项

“用户会持续使用”“用户会付费”必须被视为待验证假设，不能通过讨论直接确认。

---

## 阶段5：产品方案设计

### 核心目的

回答：

> **我们准备怎样用一个完整的产品方案解决阶段4选中的问题。**

### 主要回答的问题

包括但不限于：

- 产品核心体验是什么？
- 用户进入产品后获得价值的主路径是什么？
- 哪些问题由AI主动解决？
- 哪些问题由用户主动触发？
- 学习、知识、做题、案例、论文等是否需要形成连续体验？
- 个性化应体现在哪里？
- 产品怎样让用户感受到持续进步？
- 产品怎样形成备考生命周期内的持续价值？
- 免费与付费体验如何形成合理差异？
- 产品方案怎样体现相对普通AI的差异化？
- 哪些产品方案最值得优先验证？

### 输入

- 产品定位；
- Target User；
- Core Problem；
- Value Proposition；
- 商业假设；
- MVP Boundary；
- 阶段3的用户和考试现实。

### 输出

- 产品核心方案；
- 核心用户价值路径；
- 产品主要场景；
- 产品体验原则；
- 功能方向；
- 个性化方向；
- 付费价值承载方式；
- 需要的平台能力候选。

### 注意事项

产品方案设计优先回答：

> **产品应该怎样解决问题。**

不要提前被 Agent、RAG、模型、JSON、数据库等技术结构限制。

---

## 阶段6：产品能力设计

### 核心目的

回答：

> **为了实现已经确认的产品方案，平台必须稳定具备哪些有业务价值的能力。**

当前对“能力”的理解：

> **Capability = 为实现产品目标，系统能够稳定完成的一类有业务价值的事情。**

### 能力不等于技术实现

例如：

```text
RAG        ≠ 产品能力
LLM        ≠ 产品能力
Agent      ≠ 产品能力
LangGraph  ≠ 产品能力
Prompt     ≠ 产品能力
```

这些可能是后续实现某项能力的手段。

### 主要回答的问题

包括但不限于：

- 为什么需要这个能力？
- 它解决什么业务问题？
- 用户价值是什么？
- 它能够稳定完成什么？
- 它做到哪里为止？
- 它和其他能力的职责是否重叠？
- 这项能力是否真的值得进入MVP？
- 如何判断这项能力是否满足产品需要？

### 输入

- 产品方案；
- 核心用户场景；
- 产品价值路径；
- MVP Boundary；
- 用户与考试现实。

### 输出

- 产品能力集合；
- 每项能力的业务目的；
- 能力职责；
- 能力边界；
- 能力优先级；
- MVP所需能力；
- 后续详细设计和验证依据。

### 注意事项

能力定义不等于：

> 一个能力 = 一个Agent / 一个模块 / 一个服务。

具体实现留到后续阶段决定。

---

## 阶段7：MVP详细设计

### 核心目的

回答：

> **第一版产品具体长什么样，用户如何完整使用它。**

本阶段仍属于产品设计，不等同于系统设计。

### 主要回答的问题

包括但不限于：

- 第一版具体有哪些功能？
- 用户从进入产品到获得价值的完整流程是什么？
- 用户正常使用路径是什么？
- 每个功能解决什么问题？
- 功能之间如何衔接？
- 个性化在用户体验中如何体现？
- 用户状态如何影响产品体验？
- 哪些产品行为应该主动发生？
- 哪些行为必须由用户主动触发？
- 第一版哪些能力必须出现？
- 哪些能力延后？
- 用户为什么持续使用？
- 付费点出现在什么位置？
- 免费体验和付费体验如何区分？
- 如何验证核心产品体验是否成立？

### 输入

- 产品方案；
- 产品能力；
- MVP Boundary；
- 用户价值和商业价值假设；
- 核心用户场景。

### 输出

- MVP功能清单；
- 核心用户流程；
- 页面与交互方案；
- 关键产品状态；
- 产品规则；
- 能力使用关系；
- 免费 / 付费体验设计；
- MVP验证场景。

### 注意事项

本阶段必须能够在不知道最终技术实现细节的情况下，把产品说明清楚。

---

## 阶段8：系统设计

### 核心目的

回答：

> **如何用技术稳定实现已经确定的MVP产品设计。**

### 主要回答的问题

包括但不限于：

- 产品能力由哪些系统组件实现？
- 系统状态如何管理？
- User State、Current Question、Context、Memory如何承载？
- 哪些数据需要持久化？
- 动态JSON是否需要，以及如何设计？
- 哪些场景需要RAG？
- 哪些场景需要外部检索？
- 是否需要Agent？
- 是否需要多Agent？
- 是否需要Workflow / LangGraph？
- 模型如何选择？
- 上下文如何管理？
- 数据库、接口、安全、权限如何设计？
- 成本、性能、可靠性如何控制？
- AI结果如何评估和约束？
- 异常、Limit、重试、降级如何设计？

### 输入

- MVP详细设计；
- 产品能力；
- 用户流程；
- 产品规则；
- Eval目标；
- 技术和资源约束。

### 输出

- 系统架构；
- AI架构；
- 数据架构；
- Runtime流程；
- State / Memory设计；
- 模型与RAG方案；
- Agent / Workflow方案（如需要）；
- 接口与数据结构；
- 安全与权限方案；
- 成本和性能方案；
- 工程实施方案。

### 注意事项

系统设计必须服务于已经确认的产品设计。

不得因为某项技术“能做”，反向创造不必要的产品需求。

### 核心目的

### 主要回答的问题

包括但不限于：

- 产品是否按设计实现？
- AI能力是否达到预期？
- 用户是否真正获得价值？

- 是否愿意付费？
- 哪些产品假设被证实？
- 哪些被否定？

- 成本是否可接受？
- 是否具备上线条件？

# 5. 各阶段之间的关系

产品阶段不是单纯的文档传递流程。

更准确的关系是：

```text
Opportunity
    ↓
Goal / Principle
    ↓
Reality
    ↓
Problem
    ↓
Product Choice
    ↓
User Value + Business Value
    ↓
Product Solution
    ↓
Capability
    ↓
MVP
    ↓
System
    ↓
Implementation
```

也可以压缩为：

```text
有没有机会？
    ↓
为什么做？
    ↓
现实是什么？
    ↓
哪些问题值得做？
    ↓
我们怎么解决？
    ↓
平台必须会什么？
    ↓
第一版长什么样？
    ↓
技术怎么实现？
    ↓
做出来验证
```

---

# 6. 阶段与研究顺序的关系

阶段划分是产品开发主线，不等于所有研究工作必须严格按阶段编号串行。

允许出现：

```text
当前主阶段 = 阶段3

为了理解某个用户问题
提前探索阶段4、阶段5甚至阶段6的一部分问题
```

但：

> **提前探索不等于正式进入后续阶段，也不表示后续阶段结论已经冻结。**

跨阶段探索的目的应是帮助当前阶段获得更准确的业务理解，而不是提前锁定技术方案。

# 8. 当前架构欠缺的内容

当前架构已经足够作为规划地图，但距离正式产品设计仍存在明显缺口。

## 8.1 用户现实研究不足

目前缺少系统化的真实用户研究，包括：

- 用户原始问题；
- 用户真实学习行为；
- 放弃学习的原因；
- 失败原因；
- 购买培训的原因；
- 不购买的原因；
- 免费资源使用行为；
- 通用AI使用行为；
- 用户持续使用学习产品的原因；
- 用户流失原因；
- 用户付费行为；
- 不同用户群体之间的差异。

## 8.2 考试 / 教材现实尚未闭环

目前仍需继续研究：

- 教材、大纲和真实考试的边界；
- 教材外知识的真实要求；
- 教材内知识组合要求；
- 教材内外知识融合要求；
- 知识迁移和应用要求；
- 三科不同的考试能力要求；
- 哪些要求稳定；
- 哪些要求具有不确定性；
- 哪些结论只是经验判断，需要进一步验证。

## 8.3 商业行为证据不足

这是当前最明显的缺口之一。

需要研究：

- 用户为什么愿意为软考学习付费？
- 为什么不愿意付费？
- 普通AI的免费能力能替代到什么程度？
- 什么价值足以形成差异化？
- 用户为什么持续使用？
- 什么是备考生命周期内合理的留存？
- 用户通过考试后自然流失应该如何理解？
- 免费与付费的价值边界在哪里？
- 什么收费模式更合理？
- 用户愿意支付的价值和价格区间是什么？
- 收入是否能够覆盖模型、内容、研发、运营等长期成本？

## 8.4 竞争与替代方案研究不足

需要系统比较：

- 教材；
- 题库；
- 培训机构；
- 通用AI；
- 搜索工具；
- 学习社区；
- 免费资料；
- 其他可能出现的AI备考产品。

重点不是简单比较功能，而是回答：

> **用户为什么需要在这些替代方案之外选择我们的产品。**

## 8.5 产品定位尚未形成

当前还没有正式确认：

- Target User；
- Core Problem；
- Value Proposition；
- Differentiation；
- Retention Hypothesis；
- Payment Hypothesis；
- MVP Boundary；
- Success Criteria。

因此目前不适合形成正式待评审的产品方案。

## 8.6 产品方案尚未形成

目前仍未正式确认：

- 核心产品体验；
- 核心价值路径；
- 主场景；
- 功能结构；
- 个性化机制；
- 付费价值承载；
- 用户持续价值机制。

## 8.7 产品能力尚未正式定义

虽然已经澄清“能力”的概念，但具体能力集合尚未正式研究和冻结。

## 8.8 MVP详细设计尚未开始

Normal Forward Pipeline 等内容可以作为未来输入，但目前还不能代表完整MVP设计。

## 8.9 系统设计尚未开始

当前有关：

- 动态JSON；
- Agent；
- LangGraph；
- RAG；
- Runtime Context；
- State / Memory；

等讨论，均应视为：

> **提前探索 / 技术可行性思考**

而不是正式系统设计结论。

# 9. 当前建议的工作重心

当前规划架构已经足够使用，不建议继续细化产品架构本身。

当前更值得继续投入的是：

```text
阶段3：问题与现实研究
        │
        ├── User Reality
        │
        └── Exam / Textbook Reality
                ↓
       找到真正影响通过考试的问题
                ↓
       同时补充用户购买、留存、
       免费替代和付费行为研究
                ↓
阶段4：产品定位与商业验证
```

当前重点应该回到：

> **业务事实、用户现实、考试现实和商业现实。**

而不是提前扩展系统字段、Agent结构或Runtime实现。
