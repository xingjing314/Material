# 软考AI产品架构说明 v0.2 产品战略评审

**评审人视角**：资深 AI 产品负责人 / 产品战略顾问  
**评审日期**：2026-08-12  
**文档状态**：规划草案 / 非正式待评审版（按文档自身定位）

---

## 1. 总体判断

**整体结论：基本成立，需要局部调整。**

**最核心理由**：

这份架构的最大价值在于它**明确把“技术实现”从产品主线中剥离**，并强制产品设计先回答用户价值与商业价值，再进入能力与系统。这在当前大量 AI 产品“先画 Agent / RAG / LangGraph，再倒推用户价值”的现实中，是难得的正确方向。

主线逻辑（Opportunity → Reality → Problem → Product Choice → Solution → Capability → MVP → System）基本符合真实 Product Discovery 规律，没有明显逻辑倒置，也没有为了结构漂亮而强行制造无业务价值的阶段。

但它仍存在三个结构性不足，足以影响后续做错产品的风险：

1. **商业验证启动偏晚，且与“产品定位”绑定过紧**，导致早期机会判断缺少“是否值得付费”的硬约束。
2. **阶段5-6-7的边界在实际操作中容易滑向“过度结构化”**，尤其是“产品能力设计”独立成一级阶段，容易重新引入系统架构思维。
3. **对教育类 AI 产品特有的“教学效果可验证性”与“AI 错误风险”缺少足够权重**，这两个问题如果在 Reality 阶段不被严肃对待，后续 MVP 很容易做成“看起来很智能、实际帮助不大甚至有害”的产品。

总体属于“方向正确、骨架可用、需要局部重构与权重调整”的状态，**不建议整体推倒重来**。

## 2. 最值得保留的设计

以下设计是正确且应尽量保留的，原因如下：

1. **明确的 Platform Goal（帮助用户通过考试）+ 三轴并行约束（用户价值 × 商业价值 × 实现可行性）**  
   这比单纯“解决用户痛点”更接近真实产品决策。尤其是把“商业价值”与“用户价值”并列，而不是默认“有用就会付费”，这是成熟产品思维的体现。

2. **Validation / Eval 作为横向机制，而非最终测试阶段**  
   这是对的。不同阶段验证不同类型的假设（理解假设 → 价值假设 → 方案假设 → 体验假设 → 系统假设），比把 Eval 塞进最后阶段更符合 Lean 与 Product Discovery 实践。

3. **刻意把 MVP 详细设计（阶段7）与系统设计（阶段8）分离**  
   对 AI 产品尤其必要。AI 产品最容易陷入“技术能做 → 产品应该做”的反向驱动。强制先把“产品第一版应该是什么”说清楚，再谈实现，能显著降低做错功能的概率。

4. **对“产品能力 ≠ 技术实现”的清晰区分**  
   文档明确指出 RAG / Agent / LangGraph / Prompt ≠ 产品能力，这是当前最需要被反复强调的认知。后续如果能守住这条边界，就能避免架构重新滑向系统工程。

5. **对软考产品特殊性的初步敏感（“通过考试后离开可能是成功”）**  
   这比机械套用互联网产品的“无限长期留存”更诚实。架构为后续研究“备考生命周期内有效留存”留了位置，这是正确的。

6. **阶段3把 User Reality 与 Exam/Textbook Reality 放在同一阶段并行研究**  
   这比“先研究用户、以后再研究考试要求”更合理。真正影响“通过考试”的问题，几乎都是两者的交集。分开研究会产生大量伪问题。

这些设计构成了文档的核心护城河，后续调整应尽量围绕它们展开，而不是削弱它们。

## 3. 重大问题

按严重程度排序（只列真正影响产品设计主线的问题）：

### Critical
无。  
当前架构没有致命到“按它执行几乎必然做出错误产品”的结构性错误。

### High

1. **商业验证启动时机偏晚，且与产品定位过度绑定**  
   阶段4才集中处理“为什么愿意付费 / 为什么不用免费AI替代 / 收入能否支撑长期存在”。但在阶段1（机会与市场理解）和阶段3（问题与现实研究）中，已经有大量与付费行为相关的问题被提出。  
   结果是：早期机会判断缺少“付费意愿”的硬过滤，容易在“用户有痛点”上过度投入，直到阶段4才发现商业不成立。  
   **风险**：做出一个用户“觉得有用但不愿意付费、或付费后快速流失”的产品。

2. **阶段6“产品能力设计”独立成一级阶段，边界容易模糊**  
   文档对“能力”的定义是正确的（有业务价值的、系统能稳定完成的事情），但在实际操作中，团队很容易把“能力”写成“诊断Agent + 路径规划Agent + 知识点RAG + ……”，重新滑向系统设计。  
   当“能力”被过度结构化后，阶段7的MVP详细设计就会变成对能力的拼装，而不是对用户体验的设计。

3. **对“教学效果可验证性”与“AI错误风险”的权重不足**  
   软考是高 stakes 考试。AI 给出错误知识点、错误解题路径、错误论文框架，可能直接导致用户失败。文档把这些风险主要放在后期系统实现与 Eval 中处理，但在阶段3（现实研究）和阶段4（价值验证）中缺少足够前置。  
   **风险**：做出一个“体验流畅、看起来很智能、但实际通过率提升不显著甚至有害”的产品。

### Medium

1. **用户获取（Acquisition）与激活（Activation）在规划中几乎空白**  
   即使产品价值成立，如果用户不知道、不信任、或第一次使用无法感知价值，商业闭环仍无法成立。这些内容目前既没有独立位置，也没有被明确要求纳入阶段3/4。

2. **竞争与替代方案研究被放在“当前欠缺”中，但未在阶段结构中获得足够权重**  
   文档承认竞争研究不足，但阶段划分本身没有强制要求在阶段1或阶段3就系统回答“用户为什么需要在教材/题库/培训/通用AI之外再选择我们”。这容易导致差异化停留在口头。

3. **阶段5（产品方案）与阶段7（MVP详细设计）的边界在实践中容易重复**  
   两者都在回答“产品怎样解决问题”，只是粒度不同。如果阶段5写得过细，阶段7就变成重复劳动；如果阶段5写得过粗，阶段7又缺少足够输入。

### Low

1. **部分输出物（如用户六维 Definition 初始框架、Reasoning Frame）在阶段2就出现，容易被后续当成“事实”而非“假设”**  
   文档已提醒“应被视为研究框架”，但实际执行中仍有被固化的风险。属于执行纪律问题，而非架构本身问题。

## 5. 阶段之间的关系评审

**应合并 / 降级**
- **阶段6（产品能力设计）**：建议不再作为独立一级阶段。它更适合作为阶段5输出后的“能力清单约束”与阶段7输入前的“能力可行性检查”。独立成阶段会显著增加滑向系统架构的风险。

**应前移**
- **商业假设的形成**：从阶段4前移到阶段1（初步）与阶段3（行为现实研究）。阶段4重点做验证与选择，而不是从零开始讨论“用户是否愿意付费”。
- **竞争与替代方案研究**：应在阶段1与阶段3就被强制要求，而不是作为“当前欠缺”事后补充。

**应后移**
- 无必须后移的内容。系统设计（阶段8）已经正确后置。

**应并行**
- 阶段3内部的 User Reality 与 Exam Reality 已经正确并行。
- 用户价值与商业价值在阶段4并行是正确的，但应补充“教学效果可验证性”作为第三并行约束（尤其对教育产品）。

**应作为横向机制**
- Validation / Eval（已正确设置）。
- 建议新增横向机制：**教学效果可验证性（Learning Outcome Validation）** 与 **AI 错误风险控制**。它们贯穿阶段3-9，而不是某个阶段的专属工作。

**边界需要更清晰**
- 阶段5（概念方案）与阶段7（详细MVP体验）之间必须强制区分粒度，否则容易重复劳动。

## 6. 产品视角完整性检查

### User Value
覆盖较好。服务谁、解决什么、为什么重要、为什么AI适合、用户能否感知价值，在阶段4被明确要求。  
**不足**：对“教学效果是否真正提升通过率”的验证要求不够前置。用户感知的“感觉有帮助”与真实“通过率提升”之间可能存在巨大鸿沟。

### Business Value
覆盖方向正确，但时机偏晚。为什么选择我们、为什么不用免费AI、为什么持续使用、为什么愿意付费、收入能否支撑，都被提出。  
**不足**：缺少对“备考生命周期结束后的自然流失”如何转化为商业成功（而非失败）的明确框架；对获客成本与付费转化的约束不够强制。

### Feasibility
文档正确把它定位为约束而非主导轴，且明确当前阶段以用户价值与商业价值优先。  
**不足**：对“内容与模型成本是否可持续”“AI错误导致的用户伤害风险”的可行性讨论偏后。对教育AI产品而言，这两点应更早进入可行性约束。

### 是否还存在缺失的重要一级维度？
建议增加一个**准一级维度**（不一定要变成新阶段，但必须在关键决策中被强制考虑）：

**Learning Efficacy & Risk（教学效果与风险）**

- 产品是否真正提升通过概率？
- AI 错误答案 / 错误路径对用户的潜在伤害有多大？
- 用户如何判断“这个AI是可靠的”？
- 内容质量与知识准确性如何被持续保障？

对软考这类高 stakes 教育产品，这个维度的重要性不亚于传统三轴中的任意一轴。可以把它作为横向机制，或在阶段3、4、7中强制要求输出相关假设与验证计划。

## 7. 当前架构最大的遗漏

按重要程度排序（如果不补，未来最可能做出什么样的错误产品）：

1. **教学效果的真实可验证性（Learning Outcome）**  
   如果不严肃研究“什么样的产品行为真正提升通过率，而不是只让用户感觉被服务了”，最可能做出一个体验流畅、数据好看、但真实通过率提升不显著的产品。用户最终会用考试结果投票。

2. **AI 错误风险与用户信任建立机制**  
   软考答案错了代价很高。如果不在早期研究“用户如何判断AI是否可信”“产品如何处理不确定知识”“错误发生后如何补救”，产品很容易在上线后因一次严重错误失去信任。

3. **用户获取与首次价值感知（Acquisition + Activation）**  
   即使价值成立，如果用户不知道产品、不信任、或第一次使用无法在短时间内感知“这比通用AI更有用”，商业闭环无法启动。当前架构几乎把获客与激活当作后期运营问题。

4. **竞争与替代的真实替代强度（尤其是免费通用AI）**  
   文档承认研究不足，但架构本身没有强制要求在机会与现实阶段就回答“用户为什么必须离开 ChatGPT / 通义 / Kimi 来用我们”。这会导致差异化停留在功能层面，而不是价值层面。

5. **内容与模型成本的可持续性 + 内容运营机制**  
   教育产品的核心资产往往是高质量、持续更新的内容与知识体系。当前架构对“谁生产内容、如何保证质量、成本是否可覆盖”的讨论偏弱。AI 产品很容易低估内容运营的长期成本。

6. **上线后的持续迭代与数据闭环**  
   阶段9提到验证与修正，但对“上线后如何用真实用户数据持续改进教学策略与产品”缺少足够位置。教育产品通常需要长期数据飞轮才能真正拉开差距。

以上遗漏**不建议全部变成新的一级阶段**。更合理的处理是：
- 1、2 作为横向机制或阶段3/4/7的强制输出；
- 3、4 纳入阶段1与阶段3；
- 5、6 在阶段4商业验证与阶段9中明确要求。

## 8. 推荐的产品设计规划架构

现有9阶段骨架基本可用，建议做**局部调整**而非整体重构。核心变化：

- 将原阶段6（产品能力设计）**降级**，不再作为独立一级阶段。
- 强化商业假设的前移与竞争研究权重。
- 增加“教学效果与风险”作为贯穿机制。
- 明确阶段5与阶段7的粒度边界。

推荐结构如下（共8个一级阶段 + 横向机制）：

**横向机制（贯穿全程）**
- Validation / Eval（已有，保留并细化）
- Learning Efficacy & AI Risk（新增，教学效果可验证性 + AI错误风险控制）
- 用户价值 × 商业价值 × 实现可行性 三轴约束（已有，保留）

**一级阶段**

1. **机会与市场理解**  
   - Core Question：为什么存在值得做的软考AI产品机会？替代方案（尤其是免费AI）的威胁有多大？  
   - Main Input：市场背景、用户动机、现有备考方式、替代方案、AI带来的新可能性  
   - Main Output：机会空间描述、初步商业假设、替代方案威胁评估、值得继续研究的问题空间

2. **产品目标与原则**  
   - Core Question：平台最终负责什么、明确不负责什么？  
   - Main Input：阶段1理解、考试本质初步认识、产品边界风险  
   - Main Output：Platform Goal、产品边界、基础业务原则、待验证的用户理解框架（明确标注为假设）

3. **问题与现实研究**  
   - Core Question：真正影响用户通过考试的问题是什么？（User Reality × Exam Reality × Behavior Reality × Competition Reality）  
   - Main Input：用户反馈与行为、教材/大纲/真实考试、培训与替代方案观察、购买/留存/放弃/免费使用行为  
   - Main Output：真正影响通过的问题集合、用户行为现实、竞争与替代现实、候选用户分类、后续需验证的核心问题

4. **产品定位与商业验证**  
   - Core Question：我们为谁、解决什么核心问题、提供什么差异化价值，且用户是否愿意在备考周期内持续使用并付费？  
   - Main Input：阶段3的问题与现实、初步商业假设、竞争现实  
   - Main Output：Target User、Core Problem、Value Proposition、Differentiation、Retention Hypothesis（备考生命周期内）、Payment Hypothesis、MVP Boundary、Success Criteria、需要继续验证的假设

5. **产品方案设计（概念级）**  
   - Core Question：我们准备用怎样的完整产品方案解决已选中的问题？核心价值路径是什么？  
   - Main Input：定位、核心问题、价值主张、MVP边界、用户与考试现实  
   - Main Output：产品核心方案、核心用户价值路径、主要场景、体验原则、个性化方向、付费价值承载方式、所需产品能力候选清单（仅作为约束，不做详细设计）

6. **MVP详细设计**  
   - Core Question：第一版产品具体长什么样？用户如何从进入到感知价值，并完成一次完整的备考价值闭环？  
   - Main Input：产品方案、能力候选、MVP边界、价值与商业假设  
   - Main Output：MVP功能与体验清单、核心用户流程、关键状态与规则、免费/付费体验区分、教学效果可感知设计、MVP验证场景

7. **系统设计**  
   - Core Question：如何用技术稳定实现已确定的MVP产品设计？  
   - Main Input：MVP详细设计、产品规则、Eval目标、资源约束  
   - Main Output：系统架构、AI架构、数据与状态设计、模型与检索方案、成本/性能/风险控制方案、工程实施方案

8. **实现、验证、试用与上线**  
   - Core Question：产品是否真正帮助用户、是否稳定、是否具备可持续的商业与运营基础？  
   - Main Input：MVP设计、系统设计、成功标准、假设清单  
   - Main Output：可运行产品、Eval与试用结果、留存与付费验证、产品与系统修正、上线决策、上线后迭代与内容运营机制

**说明**：原阶段6的“产品能力”不再独立成阶段，而是在阶段5输出“能力候选清单”，在阶段6（原7）中作为MVP必须具备/可延后的约束使用。这样既保留了“能力 ≠ 技术”的正确认知，又降低了滑向系统架构的风险。

## 9. 与原架构的差异

| 变化类型 | 内容 | 原因 |
|----------|------|------|
| 保留 | 阶段1、2、3、4、7（现6）、8（现7）、9（现8）的核心问题与逻辑 | 方向正确，边界清晰 |
| 保留并强化 | Validation作为横向机制；三轴约束；MVP与系统设计分离；能力≠技术的区分 | 这些是架构最有价值的部分 |
| 降级 | 原阶段6“产品能力设计” | 独立成一级阶段后极易滑向系统架构；更适合作为方案与MVP之间的约束输出 |
| 前移 | 商业假设形成、竞争与替代研究、行为现实（购买/留存/放弃/免费使用） | 避免到阶段4才发现商业不成立或差异化不足 |
| 新增横向 | Learning Efficacy & AI Risk | 教育高stakes产品必须把教学效果与错误风险前置，否则容易做出“感觉有用但实际帮助有限甚至有害”的产品 |
| 边界澄清 | 阶段5只做概念级方案与价值路径；详细体验与流程放到MVP阶段 | 减少重复劳动，强制粒度区分 |
| 补充输出要求 | 阶段1增加“初步商业假设+替代威胁评估”；阶段3明确纳入行为与竞争现实；阶段8（原9）补充上线后迭代与内容运营 | 补足最大遗漏，但不新增一级阶段 |

整体变化幅度属于**局部调整**，而非推倒重来。主线逻辑与反技术驱动的立场被完整保留。

## 10. 当前项目下一步

基于文档自身承认的现状（用户现实研究不足、考试现实未闭环、商业行为证据不足、产品定位尚未形成），**现在最值得继续研究的工作**如下（严格按优先级，且全部停留在业务事实与假设验证层面，不进入系统实现）：

1. **系统化收集真实用户行为与付费现实（最高优先级）**  
   重点回答：用户为什么购买培训/题库？为什么不买？为什么使用通用AI？在什么情况下会持续使用某个工具？通过考试后的行为是什么？愿意为“确定感/诊断/路径/纠错”中的哪些价值付费？价格敏感区间大致在哪里？  
   没有这些证据，阶段4的任何定位都只能是讨论。

2. **完成教材 / 大纲 / 真实考试的差异研究，并识别“真正影响通过”的问题集合**  
   重点不是再堆教材内容，而是找出：哪些知识是稳定要求？哪些是组合与迁移要求？哪些是教材外但真实考试需要的？三科差异有多大？用户最容易在哪里失败？  
   这是阶段3的核心产出，也是后续所有产品选择的基础。

3. **对“免费通用AI替代强度”做专门研究**  
   用真实备考场景测试：用户用 ChatGPT / 通义 / Kimi 等解决软考问题时，在诊断、路径规划、错题归因、论文框架、不确定性处理上分别能做到什么程度？哪里明显不够？用户是否感知到不够？  
   这直接决定差异化是否真实存在。

4. **形成并小范围验证“备考生命周期内有效留存”与“付费价值”的初步假设**  
   不要直接设计收费方案，而是先回答：用户在备考的哪个阶段最需要持续陪伴？什么价值让他愿意为“确定性”付费，而不是继续用免费AI？通过考试后离开是否应被视为成功？  
   用访谈或轻量实验验证，而不是内部讨论确认。

5. **明确“教学效果如何被验证”的初步标准**  
   即使现在还做不出完整Eval，也要先定义：我们未来如何知道产品真的提升了通过概率，而不是只提升了用户满意度？哪些中间指标（诊断准确率、路径完成率、错题归因有效性等）可以提前观测？  
   这能防止后续MVP设计只优化体验、不优化结果。

以上五项完成后，再进入正式的产品定位与方案设计，风险会显著降低。当前最应该避免的，是在用户现实与商业现实证据不足的情况下，继续细化能力清单、JSON结构或Agent流程。

---

**评审总结一句话**：  
这份架构是一份**方向正确、反技术驱动意识强、骨架可用**的规划地图。它最大的价值是强制产品先回答“值不值得做”和“用户是否愿意付费”，而不是“技术能不能做”。局部调整（降级能力阶段、前移商业与竞争研究、增加教学效果与风险横向机制）后，它足以指导后续把一个软考AI产品正确地设计出来，并能有效降低做错产品的风险。
