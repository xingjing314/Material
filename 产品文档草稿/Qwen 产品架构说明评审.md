# 《产品架构说明v0.2》评审报告

## 1. 总体判断

**整体判断：基本成立，但需要进行局部结构调整与维度补全。**

**核心理由：**
这份架构说明展现了极高的产品成熟度。它最成功的地方在于**极力克制了AI产品常见的“技术自嗨”**，通过强制隔离“产品设计”与“系统设计”，并引入“三轴模型”和“横向Eval机制”，确保了产品始终围绕“帮助用户通过考试”这一北极星指标展开。它对“考过即流失”的客观规律认知也非常清醒。

然而，从完整的商业产品视角来看，当前架构在**中后段（阶段4-7）存在概念重叠与颗粒度混乱**，且在商业闭环中**缺失了“获客（GTM）”与“教研内容供应链”** 这两个决定低频应试产品生死的关键维度。如果不做调整，极易导致产品设计陷入“功能堆砌”或“叫好不叫座（有留存无利润）”的困境。

---

## 2. 最值得保留的设计

以下设计非常精准，应作为后续迭代的“宪法”予以保留：

1. **“三轴模型”（User Value, Business Value, Feasibility）**：完美契合IDEO设计思维与Lean Startup精髓，确保产品不偏科，防止“拿着AI锤子找钉子”。
2. **阶段7（MVP设计）与阶段8（系统设计）的物理隔离**：这是本架构最出彩的防御性设计。它从根本上杜绝了“因为用了LangGraph/Agent，所以产品必须这么交互”的技术反噬现象。
3. **横向机制 Validation / Eval**：将验证贯穿全生命周期，而不是作为上线前的“测试环节”。对于存在幻觉风险的AI教育产品，这是保证教学效果的底线。
4. **对“备考生命周期留存”的清醒认知**：没有陷入传统SaaS对DAU/MAU的盲目迷信，承认“通过考试即自然流失”是产品的成功而非失败，这为后续设计合理的收费模式（如按周期订阅、按结果对赌）奠定了认知基础。

## 3. 重大问题

| 严重级别 | 问题描述 | 影响 |
| :--- | :--- | :--- |
| **High** | **中后段阶段（4、5、6、7）概念重叠，线性流转不符合敏捷现实。** “产品方案”、“产品能力”、“MVP详细设计”在实际操作中是高度交织的。强行拆分为三个独立阶段，会导致严重的文档冗余，且“能力设计”极易滑向系统架构设计。 | 导致团队在PPT和文档上浪费大量时间，MVP迭代迟缓。 |
| **High** | **商业验证中缺失“获客（Acquisition/GTM）”与“单位经济模型（LTV/CAC）”。** 架构中只探讨了“用户为什么付费（意愿）”，但未规划“用户如何发现我们（渠道）”以及“获客成本是否低于生命周期价值”。软考是典型的低频、强季节性的“一锤子买卖”，获客成本往往决定商业模式的生死。 | 可能做出一个用户愿意用、也愿意付费，但买量成本远高于收入，最终亏本破产的产品。 |
| **Medium** | **“教研内容供应链”作为核心资产的缺位。** AI只是交付外壳，软考产品的真正壁垒是“教研（知识图谱、采分点Rubric、高质量范文）”。架构中将教材现实作为输入，但未将“教研内容的生产、AI对齐与品控”作为核心产品能力。 | AI产生幻觉或批改不准，导致产品口碑崩盘，沦为“高级聊天机器人”而非“辅导老师”。 |

## 4. 九阶段逐阶段评审

| 阶段 | 是否合理 | 主要优点 | 主要问题 | 建议 |
| :--- | :--- | :--- | :--- | :--- |
| **1. 机会与市场理解** | 合理 | 宏观视角好，不预设功能。 | 缺少对“流量分布与获客渠道”的初步摸底。 | 增加对现有软考流量池（如贴吧、B站、机构SEO）的观察。 |
| **2. 产品目标与原则** | 合理 | 明确“不做什么”比“做什么”更重要。 | 略显务虚。 | 保留，但需输出明确的“产品边界清单（Non-goals）”。 |
| **3. 问题与现实研究** | **非常合理** | User + Exam 双现实并行，抓住了应试产品的核心。 | 缺少“替代方案现实”（用户现在用免费AI/盗版题库怎么解决的）。 | 将“竞争与替代方案现实”纳入本阶段。 |
| **4. 定位与商业验证** | 部分合理 | 涵盖了用户价值与商业价值。 | 商业验证偏向“意愿”，缺乏“获客成本”与“商业模型测算”。 | 将GTM策略和LTV/CAC模型假设纳入本阶段。 |
| **5. 产品方案设计** | **需合并** | 关注核心体验。 | 与阶段7（MVP）边界模糊，容易变成“画大饼”。 | 与阶段7合并为“解决方案与MVP体验设计”。 |
| **6. 产品能力设计** | **需重构** | 试图抽象出平台能力。 | 极易滑向技术架构（如把RAG当能力），且忽略了“教研能力”。 | 重构为“AI能力与教研内容供应链设计”。 |
| **7. MVP详细设计** | 合理 | 聚焦第一版落地。 | 受限于前置阶段的重叠。 | 吸收原阶段5的内容，聚焦核心用户旅程。 |
| **8. 系统设计** | 合理 | 纯粹的技术实现视角。 | 无。 | 保留，严格作为技术工程阶段。 |
| **9. 实现与上线** | 合理 | 闭环验证。 | 无。 | 保留，增加“冷启动策略”的验证。 |

## 5. 阶段之间的关系评审

*   **应合并**：原阶段5（产品方案）、阶段6（能力）、阶段7（MVP）界限过于人为化。建议合并重组为 **“阶段5：产品方案与MVP体验”** 和 **“阶段6：AI能力与内容供应链”**。
*   **应前移**：**商业验证中的“获客与流量假设”** 应该前移到阶段1和阶段3。如果一开始就知道某个细分人群（如体制内评职称）的获客成本极高且无法触达，就不应将其作为Target User。
*   **应作为横向机制**：**“教研品控与AI护栏（Content QA & Guardrails）”**。软考AI产品不能仅靠代码Eval，必须有一套持续的“专家抽检、Bad Case修复、Prompt调优”的横向运营机制。

---

## 6. 产品视角完整性检查

*   **User Value（用户价值）**：**完整**。对痛点、动机、替代方案的分析框架很扎实。
*   **Business Value（商业价值）**：**有缺陷**。缺失了**Acquisition（获客）**和**Growth（增长）** 视角。低频考试产品的商业价值不仅在于“用户愿意付多少钱”，更在于“我们能以多低的成本找到他们”。
*   **Feasibility（可行性）**：**有缺陷**。包含了技术可行性，但缺失了**Domain Feasibility（领域教研可行性）**。即：我们是否有能力构建出足以让AI准确批改“高项论文”的“黄金标准数据集（Golden Dataset）”和评分Rubric？
*   **缺失的重要一级维度**：**Content & Pedagogy（内容与教研）**。在AI教育产品中，AI是引擎，教研内容是燃料。没有高质量的燃料，引擎再好也跑不远。

---

## 7. 当前架构最大的遗漏

如果不补充以下内容，未来最可能做出的错误产品是：**一个技术很炫、交互很好，但批改经常出错被考生骂上小红书，且买量成本极高导致无法盈利的“玩具”。**

1.  **获客漏斗与GTM策略（Go-to-Market）**：软考具有极强的季节性（考前3个月是高峰）。产品架构中必须规划：流量从哪里来？是靠SEO、抖音切片、还是私域裂变？CAC（获客成本）是多少？
2.  **教研内容供应链与AI对齐（Content Pipeline & Alignment）**：AI不懂什么是“高项论文的采分点”。谁来拆解教材？谁来写Prompt？谁来定义“好论文”的标准？如何防止AI在案例分析中“胡说八道”？这不仅是系统问题，更是核心的产品运营问题。
3.  **冷启动与数据飞轮策略**：MVP上线时没有用户数据，AI效果必然有瑕疵。如何设计“Human-in-the-loop（人工介入）”机制？如何诱导早期用户留下高质量的反馈数据来反哺模型？

## 8. 推荐的产品设计规划架构

建议将原有的9阶段优化为 **7个核心阶段 + 2个横向机制**，使其更符合AI教育产品的敏捷落地逻辑。

### 核心阶段
| 阶段名称 | Core Question (核心问题) | Main Input (主要输入) | Main Output (主要输出) |
| :--- | :--- | :--- | :--- |
| **1. 市场与用户现实** | 谁在考？为什么考？现在怎么学？流量在哪？ | 市场数据、用户访谈、竞品分析、流量渠道观察。 | 用户画像假设、痛点集合、初步获客渠道假设。 |
| **2. 考试与教研现实** | 考试到底考什么？教材与真题的Gap在哪？如何定义“标准答案”？ | 大纲、教材、历年真题、阅卷规则、专家教研经验。 | 考试能力模型、知识图谱、核心考点与评分Rubric（基准）。 |
| **3. 定位与商业模型** | 我们为谁解决什么？怎么赚钱？怎么获客？算得过账吗？ | 阶段1、2的输出，LTV/CAC测算，商业竞品分析。 | Target User、Value Proposition、GTM策略、商业模式假设。 |
| **4. 方案与MVP体验** | 第一版产品长什么样？用户的核心“Aha Moment”是什么？ | 阶段3的定位，用户核心旅程，MVP边界。 | 核心用户流程图、MVP功能清单、交互原型、免费/付费边界。 |
| **5. AI能力与内容供应链** | 平台必须具备哪些AI能力？教研内容如何生产并与AI对齐？ | MVP需求、教研基准、AI技术边界。 | AI能力清单（如：论文批改引擎）、Prompt库、内容生产SOP、人工介入机制。 |
| **6. 系统与工程实现** | 技术上如何稳定、低成本地实现上述设计？ | 阶段4、5的输出，技术资源约束。 | 系统架构、数据流、模型选型、RAG/Agent方案、工程排期。 |
| **7. 上线、运营与迭代** | 产品是否有效？如何冷启动？如何形成数据飞轮？ | 可运行产品、种子用户、运营策略。 | 内测数据、Eval报告、Bad Case库、迭代计划、商业化验证结果。 |

### 横向机制（贯穿始终）
1.  **Validation & Eval**：验证商业假设、产品体验、AI准确率（特别是教研采分点的准确率）。
2.  **Content QA & Guardrails**：内容品控与AI护栏，确保AI不产生误导性教学，处理Bad Case。

---

## 9. 与原架构的差异

*   **保留**：三轴模型、横向Eval机制、物理隔离产品与系统设计、对“考过即走”的正确认知。
*   **删除/合并**：删除了原阶段5、6、7之间人为制造的繁琐边界，将其重组为更符合实操的“方案与MVP”和“AI与内容供应链”。
*   **新增**：
    *   在阶段1新增了**流量与获客渠道**的考量。
    *   将原阶段3的“考试现实”升级为**阶段2“考试与教研现实”**，确立了教研内容的基石地位。
    *   在阶段3明确了**GTM与单位经济模型（LTV/CAC）**。
    *   新增了**内容供应链与AI对齐**作为独立阶段（阶段5）和横向机制。

---

## 10. 当前项目下一步

基于当前状态，建议立即停止在系统字段、JSON结构或Agent框架上的过度设计，将精力集中在以下 **4项核心Product Discovery工作** 上：

1.  **跑通“算账”逻辑（商业验证）**：调研目前软考培训市场的获客成本（如信息流投放、机构代理费），估算我们产品的LTV，验证“用户愿意付的钱”是否足以覆盖“获客成本 + AI Token成本 + 教研成本”。
2.  **构建“高项论文/案例”的AI评分基准（教研现实）**：不要等系统开发完。现在就用现成的通用大模型（如Claude 3.5 / GPT-4o），结合教材和历年真题，手动编写Prompt和评分Rubric，测试AI批改论文的准确率。**如果通用模型+好Prompt达不到及格线，后续的AI产品设计就需要重新评估。**
3.  **定义MVP的“Aha Moment”（方案验证）**：明确用户在产品中的哪一个瞬间会觉得“这玩意真有用，我愿意掏钱”。是“一键生成论文大纲”？还是“精准指出案例分析的漏答点”？围绕这个瞬间设计极简原型。
4.  **摸底流量池（GTM验证）**：去小红书、抖音、B站、软考贴吧观察，现在的考生在哪里聚集？他们为什么会被某些内容吸引？我们的MVP该如何包装成内容去低成本获取第一批种子用户。
